# DARFUS C3 — Common Profile Field Matrix (Pre-Edit)

Control: `DARFUS-CLIENT-C3-COMMON-PROFILE-FIELDS-EXACT-PARITY-01`  
Mode: read-first / minimum-safe implementation boundary  
Profiles in scope: GBW, GBP, Diamond, Gem Stone, Pearl (represented by the current nine internal strategies).

## Evidence boundary

The upstream client audit identifies the shared client inventory requirement as the common set headed by Barcode, SKU, RFID, Item Type, Description, Brand, Supplier, Purchase Date, Image, Status, Branch, Created By/Date, and Audit Log. The current workspace does not contain the original five profile DOCX files; the client requirement below is therefore traced to the accepted upstream C1/Phase-35C authority records already present in `docs/client-requirements/`. No field absent from those records is treated as a new business requirement.

`SharedReceiveSection` is a single reusable intake component already used by the five accepted profile families. It owns the common receive envelope fields Supplier, Location, Purchase Date, Tax Treatment, Notes and the read-only Tax Summary. Profile pages own only profile-specific fields and pass the envelope to the canonical Supplier Receive V2 contract.

## Pre-edit conclusion

The proven gap is not missing storage for the common receive fields. It is the absence of one explicit, reusable, server-published common-field contract and semantic coverage tests tying the shared receive envelope and Asset projections to the five top-level profiles. SKU and universal image are not proven authorities and remain outside implementation.
